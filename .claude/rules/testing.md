# Testing, feedback and pushing

`origin/main` is the only code that matters, and teammates push to it too. Work in small slices: one problem per
commit, gate it, push it right away (no waiting for earlier deploys), verify the deploy in the background.

## The gate (seconds to a couple of minutes, no local JDK needed)

1. `git fetch` and build on top of `origin/main`.
2. `workflow/bin/local.sh up`: builds the working tree with the root `Dockerfile` (the deployed JDK) and runs it on
   :8080 against the Compose Postgres. `local.sh logs` follows its log.
3. `workflow/bin/check.sh`: published `examples/*.hurl` + our `workflow/hurl/*.hurl` + the 36 parallel checks in
   `workflow/bin/race.sh` (talk limit, ratings, one email = one speaker, conflicting committee decisions, withdraw
   races, co-speaker limit/duplicates/add-remove storms, co-speaking vs the talk limit, workshop rushes), the
   consistency matrix (`consistency.py`: every talk endpoint x every format x every status, plus a missing talk:
   an existing talk never gets 404, a missing one always does, no 5xx) and replays of every harness transcript
   (`workflow/hurl/harness/`, generated by `transcripts.py`: the steps the harness accepted keep their status, the
   step it rejected must not answer that again). Must end with `ALL GREEN`.
   `check.sh <url> <file.hurl>` runs one suite.
4. `workflow/bin/compare.sh`: runs `HEAD` on :8082 beside the working tree and diffs 31 reads and rejected writes.
   `EQUIVALENT` for refactors and perf work; for a fix, the only differences are the intended ones.
5. Perf work: `workflow/bin/perf.sh` (k6, 60 users, on production-shaped data) against `workflow/perf/baseline.json`.
   The baseline records its talk count; on data more than 5 % apart it isn't compared: re-baseline.
6. Changed `Dockerfile`, `pom.xml` or `schema.sql`: also `local.sh image` (linux/amd64, like `deploy.yml`) and
   `check.sh http://localhost:8081`.

JUnit runs in CI before each deploy (`quality` job in `deploy.yml`). Check that run after pushing.

## Local data vs production

We can't read the deployed database, only its API. `workflow/bin/dbdrift.sh` profiles both through `/talks` (volume,
format/level/status mix, co-speakers, ratings per talk, accepted workshops) and exits 1 with what drifted.
`dbdrift.sh --sync` rebuilds the local test data in production's shape (synthetic rows, ~2 s; the local database is
scratch). Keep `dbdrift.sh --watch 600` running in the background; on drift, `--sync` and re-run the gate.
**Never `--sync` (or `perf.sh`, which syncs) while a check runs against the local database**: its TRUNCATE wipes
rows mid-test (it once made the workshop race checks fail on a correct build). New
tables from a feature: add them to `--sync`'s TRUNCATE and generator.

## After pushing

- `gh run watch <id> --exit-status` in the background, then `check.sh https://fagsem-h2026-team-7.scienta.cloud`
  (or the suite you touched) and `workflow/bin/feedback.sh`.
- `workflow/bin/watch.sh 10` runs in the background all session and exits when anything changes: a new commit on
  `origin/main`, a check's status, a feature released or claimed, the service down. Then `feedback.sh`, tell the user,
  restart it (`KNOWN=1` while a known failure is being worked on, so it only reports changes).
- Priority: failing checks first, then new commits on `main` (gate them: `local.sh up`, `check.sh`, `compare.sh`
  against the commit before them; then the deploy and the harness), then everything else.

## When the harness fails a check

The transcript only shows the first wrong answer; the check may have more steps after it. So: replay the
transcript (`transcripts.py` + `check.sh`), fix the step, then run `consistency.py` to find the same kind of answer
on other endpoints and kinds of talk before pushing, instead of finding out one deploy at a time. A confirmed
expectation that overrides the matrix's rule goes into `EXPECT_404` with the evidence.

## Reporting

Every iteration, to the user and as an entry in `workflow/iterations.md`:
**Problem** (what was wrong, with the number or request that shows it), **Change** (files, lines), **Evidence**
(gate results, before/after), **Pushed** (commit, deploy result, what the deployed service shows).

## Writing Hurl suites

- One file per rule (`workflow/hurl/<feature>-<rule>.hurl`): Hurl stops a file at its first failing request.
- Fresh data per run (`{{newUuid}}`), assertions scoped to your own speaker/talk.
- Spec silent on a status code: assert the range (`status >= 400`, `status < 500`); otherwise pin it.
- Specs live in `specs/<feature>.md` (fetched from the harness). A feature request isn't a spec: write the edge
  cases down before implementing.
